# Historical Rug Pattern Matching

This document specifies how the scanner should identify tokens whose deployer
wallet matches the on-chain signature of known rug-pull operators — using a
combination of self-maintained reputation data, third-party security APIs, and
behavioral heuristics derived from the deployer's on-chain history.

---

## 1. The Core Problem

Deployer profiling (`deployer_profiling.md`) tracks a specific deployer's past
projects to build a reputation score. But this only works for deployers the
scanner has already seen.

Rug Pattern Matching solves a different problem: **cross-referencing every new
deployer against known-bad patterns and public rug registries**, even on first
encounter. The goal is to catch serial ruggers who use fresh wallets by
recognizing their behavioral fingerprint.

---

## 1.5 Integration Scopes, Pipelines & Safety Score Overrides

### A. Native Contract Similarity & Audit Scope
* **Basic Scan**: Integrated in **both Backend and UI**. The Basic Scan UI displays the static contract checklist (e.g., verified contract code similarity, proxy patterns, honeypot warnings, tax rates).
* **Deep Scan**: Integrated in the **Backend**. The Deep Scan backend reuses the cached contract audit results generated by the Basic Scan, incorporating them into advanced scoring engines.

### B. Basic-to-Deep Scan Execution Pipeline
When a user triggers a Deep Scan on any token:
1. The engine **first executes the entire Basic Scan pipeline** synchronously.
2. If the Basic Scan detects a critical blocker (e.g. `isHoneypot: true` or `isRugPull: true`):
   - The Deep Scan UI prominently displays a **Critical Security Banner** at the top of the interface (e.g., `🚨 HONEYPOT DETECTED — EXIT IMPOSSIBLE`).
   - The scan continues to collect secondary metrics (such as developer history and news) but locks the risk classification to maximum danger.

### C. Safety Score Overrides (Forcing Safety Score to 0 / Risk to 100)
A token's overall **Safety Score is immediately forced to 0/100** (meaning maximum **Risk Score of 100/100**) if the scanner detects any of the following critical indicators:

| Trigger | Description | Code Condition |
|---|---|---|
| **Honeypot Detected** | Token swap simulation fails on sell transactions | GoPlus `is_honeypot = true` or Honeypot.is check |
| **Active Rug Pull** | Token liquidity pool drained or contract owner executes malicious functions | `isRugPull = true` or `lp_check` returns LP removed |
| **Severe Liquidity Problems** | Available trading liquidity drops below $100 | `totalLiquidityUsd < 100` (excludes pre-graduation curve phase) |
| **Deployer Over-Concentration** | Deployer wallet holds a majority of circulating tokens or executes massive dumps | `deployerHoldingsPct > 50%` or deployer has sold $>90\%$ of initial tokens |

## 2. Data Sources (Priority Order)

### Source 1: Native Contract Audit & Similarity Engine
Instead of querying competitor APIs like TokenSniffer, our scanner runs a native static contract parser on the backend. This parses the smart contract bytecode (retrieved via public RPC: `connection.getAccountInfo` or `provider.getCode`) to:
1. Compare code similarity against a database of known contract templates (identifying exact contract clones).
2. Check for hidden minting features, upgradeable proxy architectures, and pause switches.
3. Establish a standard checklist of failed contract security rules.

#### ✅ C-004 RESOLVED — Bytecode Similarity Database: Initial Seed & Maintenance

**Problem was**: An empty database on Day 1 means RUG-003 never fires.

**Resolution — Initial Seed Strategy**:
The bytecode registry is stored as a versioned JSON file at
`lib/reputation/data/known_rug_signatures.json`. It is seeded at launch
with signatures from the following **free public sources**:

| Source | Method | Records |
|---|---|---|
| [Etherscan Verified Source Code](https://etherscan.io/contractsVerified) | Pull ABI + bytecode for known rug addresses flagged in `known_ruggers` DB | Ongoing |
| [BSCScan Verified Contracts](https://bscscan.com/contractsVerified) | Same as above for BSC | Ongoing |
| GitHub public rug repositories | Search `honeypot solidity contract` on GitHub public repos | ~50 templates at launch |
| Community-reported rugs from admin panel | Admin flags a rug → backend fetches bytecode and appends to JSON | Manual curation |

**Hashing Strategy** (stored in the JSON file):
```typescript
interface RugSignatureEntry {
  id: string;              // e.g. "rug-eth-001"
  chain: 'eth' | 'bsc' | 'solana';
  label: string;           // Human-readable: "HoneypotBot_V3"
  // Jaccard similarity: compare set of 4-byte function selectors
  functionSelectors: string[];  // e.g. ["0x095ea7b3", "0x40c10f19"]
  // Keccak fingerprint of cleaned bytecode (metadata removed)
  bytecodeHash: string;
  addedAt: string;         // ISO date
}
```

**Matching Logic**:
```typescript
// Jaccard similarity on 4-byte selectors (function fingerprints)
function jaccardSimilarity(a: Set<string>, b: Set<string>): number {
  const intersection = new Set([...a].filter(x => b.has(x)));
  const union = new Set([...a, ...b]);
  return intersection.size / union.size;
}
// Flag as RUG-003 if similarity >= 0.85 (85% match)
```

**Auto-growth**: When the admin confirms a new rug via the admin panel, the
backend automatically fetches the contract bytecode and appends the signature
to the JSON file via a server action. The file is committed to the repo, so
it grows permanently as a version-controlled asset.

- **Cache TTL**: 24 hours (results are stable for a deployed contract)
- **Chains supported**: ETH, BSC, Polygon, Arbitrum, Base, Solana


### Source 2: GoPlus Token Security (Already Integrated)
GoPlus returns `creator_address` — this creator can be queried against GoPlus's
own bad actor registry via a separate endpoint:
```
GET https://api.gopluslabs.io/api/v1/address_security/{address}
```
Returns: `malicious_address`, `phishing_activities`, `blackmail_activities`,
`contract_address` (known malicious contracts deployed).

### Source 3: Internal `known_ruggers` Table (Self-Maintained)
A Supabase table of confirmed rug operators, populated from:
- Admin-flagged entries (manual curation)
- Auto-populated when a deployer's token is confirmed as a rug via
  community reports or post-fact analysis

```sql
CREATE TABLE known_ruggers (
  id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  deployer_address TEXT NOT NULL,
  chain           TEXT NOT NULL,

  confirmed_rugs  INTEGER NOT NULL DEFAULT 1,
  total_tokens    INTEGER NOT NULL DEFAULT 1,

  -- Evidence
  rug_token_addresses  TEXT[],        -- List of tokens that rugged
  rug_confirmed_at     TIMESTAMPTZ[],  -- When each rug was confirmed
  rug_methods          TEXT[],         -- e.g. ['lp_drain', 'mint_dump', 'honeypot']

  -- Source of entry
  source          TEXT NOT NULL,      -- 'admin', 'community', 'auto_flag'
  first_seen_at   TIMESTAMPTZ DEFAULT NOW(),
  last_updated_at TIMESTAMPTZ DEFAULT NOW(),

  UNIQUE(deployer_address, chain)
);

CREATE INDEX idx_ruggers_address ON known_ruggers(deployer_address, chain);
```

### Source 4: Behavioral Fingerprint Matching (On-Chain Heuristics)
Even without a registry hit, certain on-chain patterns strongly indicate a
serial rugger using a fresh wallet:

| Pattern | Description | Signal Weight |
|---|---|---|
| **Dev wallet funded from mixer** | Deployer wallet received SOL/ETH from Tornado Cash, Railgun, or similar | `high` |
| **Wallet age < 24h at deploy time** | Deployer wallet created the same day as the token | `medium` |
| **LP removed within 7 days** | Liquidity pulled in the first week (retroactive check) | `critical` |
| **Honeypot + immediate LP drain** | Standard honeypot execution sequence | `critical` |
| **>80% supply to deployer, then dump** | Deployer held majority, sold within 48h | `high` |
| **Multiple tokens, all failed** | Deployer made 3+ tokens all with <100 holders | `medium` |

## 3. Risk Signals Generated

| Signal ID | Source | Condition | Severity |
|---|---|---|---|
| `RUG-001` | Internal DB | Deployer in `known_ruggers` with ≥1 confirmed rug | `critical` |
| `RUG-002` | Internal DB | Deployer in `known_ruggers` with ≥3 confirmed rugs | `critical` |
| `RUG-003` | Native Audit | Failed contract similarity check (cloned from known rug) | `critical` |
| `RUG-004` | GoPlus address security | `malicious_address: true` for deployer | `critical` |
| `RUG-005` | On-chain heuristic | Deployer wallet funded from known mixer | `high` |
| `RUG-006` | On-chain heuristic | Deployer wallet created < 24h before token launch | `medium` |
| `RUG-007` | On-chain heuristic | LP removed within 7 days of launch | `critical` |

**Score Impact**: Any `critical` signal adds +25 points to the overall risk score.
Multiple `critical` signals stack (no cap at individual signal level — the
overall score is still capped at 100).

## 4. UI Display Rules

Results must be displayed as objective facts. The system reports **what
happened**, not judgments:

```
Deployer Risk Assessment:
  Contract Audit:    Failed similarity check (98% match to known rug contract)
  Confirmed Rugs:    2 previous tokens (via known_ruggers DB)
  Wallet Age:        Deployed 6 hours before this token
  LP Status:         LP removed 4 days after launch on prior token "FAKETOKEN"
```

No "RUG ALERT" badge in a red flashing box. The facts speak for themselves.
The risk score rise communicates the severity.

**Exception**: A `RUG-001` or `RUG-003` hit (confirmed scam) shows a
non-flashing, clearly visible warning panel at the top of the Deep Scan result:
```
⚠️ Deployer is associated with a previously confirmed cloned scam contract.
   See Deployer Risk section below for full details.
```

## 7. Technical Feasibility, Cost & Implementation Details

### A. Native Static Contract Parser Feasibility
- **Mechanism**: The backend loads the compiled bytecode of the contract and runs a local hash-similarity algorithm against a database of known rug contract signatures (stored in a local JSON file or Supabase database).
- **Feasibility**: **Highly Feasible**. Uses standard string similarity or hash matching (e.g. MinHash or Jaccard similarity) on the loaded bytecode.
- **Cost**: $0 (Runs locally, no third-party API keys or external competitor dependencies).
- **GoPlus Address Security API**:
  - **Mechanism**: Query `GET https://api.gopluslabs.io/api/v1/address_security/{address}?chain_id={chain_id}`.
  - **Feasibility**: **Highly Feasible**. GoPlus does not enforce strict key registration or rate limits on standard address scanning routes.
  - **Cost**: $0.

### B. Mixer Deposit Heuristic (Detecting Tornado Cash / SOL bridges)
- **Mechanism**: For the deployer address, locate the first funding transaction (the transaction that first deposited native gas tokens to the address).
  - Inspect the `from` address of this transaction.
  - Cross-reference the sender address against a static list of known privacy protocol contracts (e.g. Tornado Cash router addresses on Ethereum/BSC, Railgun, or central bridges).
  - If a match is found, flag the wallet as **mixer-funded**.
  - **Feasibility**: **Highly Feasible**. Uses static contract lists and a single contract creator lookup request.
  - **Cost**: $0 (Standard RPC node history request).
